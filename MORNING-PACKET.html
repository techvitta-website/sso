Part 3 — Your checklist, in priority order

CRITICAL  A. HRMS is leaking its admin key to the browser

This is the biggest risk across all your apps. The HRMS front-end creates a service_role Supabase client in the browser (src/integrations/supabase/client.ts, exposed as window.__supabaseAdmin). Anyone can open that site's console and run admin commands — list every user, delete records, or make themselves admin. Fixing it is two parts and order matters:

  1. Remove it from the code first. Delete the service-role client and every supabaseAdmin use in the browser (useEmployees.ts, lib/client-setup.ts, lib/client-auto-setup.ts). Those admin operations (creating employees/users) must move to the existing Supabase edge function auto-setup-client, which already runs server-side with the key safely. Also remove VITE_SERVICE_ROLE_KEY from the HRMS project's Vercel env.
  2. Then rotate the HRMS service_role key (it's compromised — treat as public). Because the app no longer ships it, rotation finally sticks.

I did not push this change: it's a refactor on a live production app and, done hastily unattended, it would break employee creation. It needs a proper edge-function move + a test. I can do it with you in one focused pass — it's the first thing to tackle.

CRITICAL  B. Anyone logged into CMS or HRMS can make themselves admin

Both apps decide "are you an admin?" from a database row the browser is allowed to edit, and the role tables have no rule stopping a user from editing their own role. So a normal HR user can set their own role to admin. The real fix is a database rule (RLS) on those tables. Run the SQL below in each app's database. Test in a quiet window — I could not test these against those databases (no access), and an over-tight rule could affect login, so read the notes.

CMS database (ref qzgzmytmfoozociuhgtp) — lock the hr_users table:

-- Signed-in users can still READ (needed for login + the team list),
-- but only admins may INSERT/UPDATE/DELETE. The hub provisions with the
-- service key, which bypasses RLS, so grants keep working.
alter table public.hr_users enable row level security;

create or replace function public.cms_is_admin()
returns boolean language sql stable security definer set search_path = public as $$
  select exists (select 1 from public.hr_users
                 where email = auth.jwt()->>'email' and role = 'admin');
$$;

drop policy if exists hr_users_select on public.hr_users;
create policy hr_users_select on public.hr_users
  for select to authenticated using (true);

drop policy if exists hr_users_write on public.hr_users;
create policy hr_users_write on public.hr_users
  for all to authenticated
  using (public.cms_is_admin()) with check (public.cms_is_admin());

-- hr_users also has a plaintext `password` column exposed to the app. Null it out.
update public.hr_users set password = null where password is not null;

Note: after this, the CMS "Edit user / change role" button will only work for admins (correct). If any non-admin flow wrote to hr_users, move it behind an edge function.

HRMS database (ref snjtkvvmjqizdfyqbyzd) — lock the user_roles table:

-- Stop users granting themselves roles. Admins (and the hub's service key)
-- can still manage roles.
alter table public.user_roles enable row level security;
revoke all on public.user_roles from anon, authenticated;
grant select on public.user_roles to authenticated;

create or replace function public.hrms_is_admin()
returns boolean language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from public.user_roles ur join public.roles r on r.id = ur.role_id
    where ur.user_id = auth.uid() and r.name = 'Admin');
$$;

drop policy if exists user_roles_select on public.user_roles;
create policy user_roles_select on public.user_roles
  for select to authenticated
  using (user_id = auth.uid() or public.hrms_is_admin());

drop policy if exists user_roles_write on public.user_roles;
create policy user_roles_write on public.user_roles
  for all to authenticated
  using (public.hrms_is_admin()) with check (public.hrms_is_admin());

Note: HRMS currently lets a brand-new "Client" self-signup insert its own user_roles row from the browser — this SQL will block that. If you rely on client self-signup, move that insert into the auto-setup-client edge function (it already exists). Also worth removing later: hard-coded email backdoors in HRMS's AuthContext (admin@tv.com → Admin, etc.) grant admin with no database check.
